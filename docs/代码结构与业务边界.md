# Offer 罗盘代码结构与业务边界说明

> 目的：让后续开发者能快速理解项目代码分工，避免把展示、业务逻辑、数据状态、接口请求混在一起，降低项目变成“屎山”的风险。

## 1. 总原则

本项目后续开发必须遵守以下边界：

```text
页面 views：负责业务流程总控、页面状态、路由跳转、调用 store / api。
组件 components：负责展示和交互事件，不直接改业务数据，不直接写 localStorage，不直接调接口。
状态 stores：负责业务状态、数据读写、localStorage 临时持久化。
接口 api：负责后端请求封装。
文档 docs：负责产品逻辑、开发法则、验收标准、交接说明。
```

核心判断标准：

- 如果代码在“决定下一步业务动作”，放在 `views` 或 `stores`。
- 如果代码只是在“展示一块 UI”，放在 `components`。
- 如果代码在“跨页面保存数据”，放在 `stores`，短期可以 localStorage，长期迁移后端。
- 如果代码在“请求后端”，放在 `api`。

## 2. 当前业务模块与代码映射

### 2.1 简历分析优化

| 文件 | 职责 | 不应该做什么 |
|---|---|---|
| `frontend/src/views/Resume.vue` | 简历分析页总控；维护 JD、简历输入、上传文件、分析状态；处理保存版本、加入投递、进入模拟面试等业务动作。 | 不继续堆大量展示模板；不把所有结果卡片都写在页面里。 |
| `frontend/src/components/ResumeAnalysisResult.vue` | 展示当前简历分析结果：投递准备度、匹配度、JD 要求、已有证据、能力缺口、改写建议、操作按钮。 | 不调接口；不保存简历；不写投递记录；不跳路由；只通过事件通知父页面。 |
| `frontend/src/components/ResumeDiagnosisContextCard.vue` | 展示求职诊断档案回流到简历分析页的补强线索。 | 不读写 sessionStorage；不修改 JD/简历；只通过事件通知父页面清除上下文。 |
| `frontend/src/stores/resume.js` | 简历历史、岗位简历版本等状态。 | 不放复杂 UI 展示逻辑。 |

## 3. 已完成的结构治理

当前已经完成以下拆分：

```text
Resume.vue
  -> ResumeAnalysisResult.vue
  -> ResumeDiagnosisContextCard.vue

Calendar.vue
  -> ApplicationBoard.vue

Profile.vue
  -> CareerDiagnosisCard.vue

多个页面 loading
  -> LoadingDots.vue
```

这不是改变用户功能，而是把代码从“一个页面塞所有东西”改成“页面总控 + 展示组件”。

---

## 4. 后续安全整理顺序

按风险从低到高：

1. `Profile.vue` 的使用记录弹窗。
2. `Interview.vue` 的面试复盘展示区。
3. `Resume.vue` 的历史详情弹窗。
5. localStorage / sessionStorage 统一封装为本地数据服务。
6. 再考虑迁移到后端数据库。

注意：

- 不允许一次性大重构。
- 每拆一个模块必须 `npm run build`。
- 涉及 store、api、路由、localStorage key 的修改必须单独评估。
- 展示组件只接收 props 和 emit 事件，不直接改变业务数据。

## 5. 交接时重点看什么

新开发者接手时优先看：

1. `docs/项目开发法则.md`
2. `docs/P0闭环验收清单.md`
3. `docs/代码结构与业务边界.md`
4. `frontend/src/views/Resume.vue`
5. `frontend/src/views/Calendar.vue`
6. `frontend/src/views/Interview.vue`
7. `frontend/src/views/Profile.vue`
8. `frontend/src/stores/*.js`

判断是否改坏主链路，只看这条：

```text
JD / 岗位
-> 简历分析
-> 保存岗位简历版本
-> 加入投递进展
-> 模拟面试
-> 面试复盘
-> 求职诊断档案
-> 回到简历优化
```
