# Offer 罗盘竞品分析教师汇报版 v2

## 一句话结论

Offer 罗盘不应该做成“又一个 AI 简历工具”，而应该做成**大学生求职过程管理与 AI 辅导系统**。

竞品已经证明：学生需要简历优化、岗位信息、模拟面试、投递记录。但目前多数产品是单点工具，学生仍然缺少一条清楚的求职行动路径。

> 外部岗位/JD -> 简历匹配分析 -> 投递准备度判断 -> 改写建议 -> 保存简历版本 -> 加入投递进展 -> JD 模拟面试 -> 面试复盘 -> 用户画像

---

## 1. 这些结论从哪里来

| 结论类型 | 来源 | 在报告里怎么使用 |
|---|---|---|
| 竞品功能 | 求职方舟、超级简历、牛客、实习僧、智联/BOSS/猎聘公开页面 | 判断竞品做了什么 |
| 用户反馈线索 | 公开问答、社区讨论、搜索结果中的常见疑问，例如收费、导出、岗位靠谱不靠谱、面试题是否有用 | 只作为方向性线索，不当成精确统计 |
| 产品体验判断 | 站在学生使用路径上判断：第一步是否清楚、结果是否有用、是否能继续行动 | 用来决定 Offer 罗盘怎么设计 |
| 开发风险 | 插件、自动投递、岗位数据维护等技术和合规问题 | 不写成“用户吐槽”，只作为内部开发边界 |

说明：上一版把“开发风险”和“用户反馈”混在一起，是不严谨的。比如“海量岗位爬取”是开发者视角，老师更关心的是用户看到岗位时能不能信、能不能用、会不会过期。

## 2. 竞品里用户真正需要的功能

| 用户需要 | 代表竞品 | 为什么重要 | Offer 罗盘应该怎么做 |
|---|---|---|---|
| 针对具体 JD 改简历 | 求职方舟、超级简历 | 学生不是缺一份通用简历，而是不知道这份简历能不能投这个岗位 | 简历分析结果固定为“岗位要求、匹配证据、能力缺口、改写建议、投递准备度” |
| 投递进展记录 | 求职方舟、表格工具 | 海投后容易忘记投了哪里、进展到哪一步 | 投递表绑定 JD、简历版本、面试记录，形成复盘链路 |
| 可靠岗位信息 | 实习僧、牛客、招聘平台 | 用户不只是要岗位多，更要知道岗位是否真实、是否过期、来源在哪里 | 岗位列表显示来源、更新时间、截止日期、状态 |
| 模拟面试 | 牛客 | 面试前需要练习，但泛泛题目帮助有限 | 面试题必须来自目标 JD 和用户简历 |
| 简历基础纠错 | 超级简历 | 学生容易犯格式、表达、量化不足等低级错误 | 作为辅助体检功能加入，但不取代 JD 匹配 |
| 结果可复盘 | 简历工具、面试工具 | 用户需要看到“我哪里变好了，下一步做什么” | 生成简历分析记录、面试复盘、个人求职画像 |

## 3. 竞品里容易让用户不满意的点

| 用户不满意点 | 用户视角的问题 | 我们怎么规避 |
|---|---|---|
| 不知道下一步做什么 | 工具很多，但用户做完分析后不知道该改简历、投递还是练面试 | 每次分析后给出明确下一步：先改/可投/加入投递表/开始模拟面试 |
| 建议太泛 | AI 说得都对，但不像针对我的简历和岗位 | 每条建议必须对应 JD 要求和简历原文证据 |
| 岗位信息不可信 | 用户担心岗位过期、来源不明、是不是还在招 | 每条岗位标来源、更新时间、截止日期和状态 |
| 收费不透明 | 用户投入时间后才发现导出或保存要付费，会反感 | 收费权益提前说明，先做内测额度，不突然卡核心流程 |
| 结果不能沉淀 | 改完一次简历就结束，下次投别的岗位还要重新来 | 保存每次 JD 分析、简历版本、投递状态和面试复盘 |
| 过度代替学生 | 如果直接代写、代投，老师和学校可能不认可 | 产品定位为辅导和训练，不是替学生完成求职 |

## 4. 重点竞品给我们的启发

### 求职方舟 AI

它证明“AI 求职工具集合”有市场：AI 改简历、AI 找工作、岗位表、投递表、会员体系都围绕学生求职。

我们要学的是：把简历、岗位、投递串起来。  
我们不急着学的是：自动填表插件、自动投递、过早支付。

### 超级简历

它证明学生需要简历成品感：模板、纠错、措辞优化、导出都很直观。

我们要学的是：简历建议要具体、清楚、有交付感。  
我们不应该走偏的是：做模板市场。Offer 罗盘核心不是简历好不好看，而是简历和 JD 是否匹配。

### 牛客

它证明面试和笔试准备是强需求，尤其是真题、面经、模拟面试。

我们要学的是：面试训练要真实、有针对性。  
我们不应该硬做的是：大而全题库和社区。短期更适合做“基于 JD 和简历的模拟面试”。

### 实习僧、智联、BOSS、猎聘

它们证明岗位信息是刚需，但这些平台主要解决“哪里有岗位”，不解决“我适不适合、该怎么准备”。

我们要学的是：岗位分类、来源、状态、外部链接。  
我们不应该做的是：和大平台比岗位数量。

## 5. 下一步开发重点

| 优先级 | 要做什么 | 目的 | 验收标准 |
|---|---|---|---|
| P0 | 重构简历分析结果 | 让用户先知道能不能投 | 结果页先显示投递准备度，再显示证据和建议 |
| P0 | 保存简历版本 | 支持不同 JD 对应不同简历 | 每次分析能保存为一个岗位版本 |
| P0 | 投递进展表持久化 | 让求职过程可持续记录 | 关闭页面后投递记录不丢失 |
| P0 | 模拟面试绑定 JD | 避免泛泛面试题 | 每道题能对应 JD 要求或简历经历 |
| P1 | 岗位列表标注可信信息 | 解决岗位是否可靠的问题 | 显示来源、更新时间、截止日期、状态 |
| P1 | 个人页做求职画像 | 把记录变成复盘价值 | 展示投递数、面试数、薄弱能力、下一步建议 |
| P2 | 会员权益草案 | 为后续商业化做准备 | 先展示权益和内测额度，不急着接支付 |

## 6. 给老师的最终判断

这个项目值得继续做，但方向要从“AI 简历工具”升级为“大学生求职过程辅导系统”。

竞品已经证明学生有需求，但也暴露出一个问题：简历、岗位、面试、投递常常是割裂的。Offer 罗盘的价值，就是把这些环节串成一条学生能照着走的路径。

我们下一步不追求功能多，而是先把核心闭环做扎实：

1. 用户拿到一个具体岗位 JD；
2. 系统判断简历和岗位是否匹配；
3. 系统告诉用户先改哪里、为什么改；
4. 用户保存这一版简历并加入投递；
5. 面试前按这个岗位训练；
6. 面试后复盘并反哺下一版简历。

只要这条路径跑通，Offer 罗盘就不是一个演示 Demo，而是可以在校园就业指导场景中持续使用的产品。
