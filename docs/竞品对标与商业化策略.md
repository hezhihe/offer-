# 竞品对标与商业化策略

> Sprint 1 输出物。本文不是商业计划书，而是按照创业指导老师的建议，用于指导 Offer 罗盘后续产品迭代的竞品分析与商业化决策文档。

## 1. 老师反馈转译

老师的核心建议不是“继续堆功能”，而是：

1. 先做好竞品分析。
2. 把当前市场上的产品都看完一遍。
3. 每个产品逐帧分析。
4. 所有功能、用户体验好的地方、不好的地方，都要详细分析。
5. 先把这个工作做完，再继续完善功能、测试、优化迭代。

这句话背后的意思是：Offer 罗盘不能只靠主观判断继续开发，必须用市场上真实产品作为参照，形成“我们为什么这样做”的产品证据链。

## 2. 错误根源

当前项目最大风险不是执行力不足，而是容易陷入“看到竞品很像，就马上照着做”的误区。

真正的问题是：大学生求职赛道已有大量产品，简历优化、模拟面试、岗位信息、自动投递、内推表、会员体系都已经有人做。如果 Offer 罗盘只复刻功能，会变成低配竞品。

正确方向是：先拆清楚市场上的产品怎么做，再判断哪些功能值得学、哪些功能暂时不做、哪些体验我们能做得更深。

## 3. 涉及的技术栈

这份文档本身不改业务代码，但它会影响后续模块的开发方向：

- Vue：简历页、面试页、招聘日历、个人页的体验设计
- Pinia：简历、岗位、面试、投递进展、用户画像状态管理
- FastAPI：简历分析、模拟面试、岗位数据、用户历史接口
- Supabase：用户画像、简历历史、面试历史、投递记录持久化
- DeepSeek：JD 拆解、简历匹配、面试追问、复盘建议
- 文档体系：产品决策、竞品分析、商业化路线、路演材料

## 4. 为什么这样做

竞品分析的目的不是写材料好看，而是减少错误开发。

如果我们不拆竞品，就会出现三个问题：

1. 做别人已经做烂的功能，没有差异化。
2. 忽略用户真正高频的工作流，只做展示型页面。
3. 商业化路径凭感觉设计，最后无法说服老师、用户和评委。

所以 Sprint 1 的优先级应该是：竞品对标文档先行，再把结论分发给各功能线程做迭代。

## 5. 对应功能是什么

本分析会直接指导以下功能：

- 简历分析优化：如何对标 AI 改简历、专岗优化、过机筛优化
- 模拟面试：如何对标 AI 面试、笔试工具和面试复盘产品
- 岗位数据与投递进展：如何对标校招表、实习表、内推码表、投递进展表
- 个人页复盘与用户画像：如何把使用记录变成持续价值
- 商业化：如何设计会员、兑换码、学校合作、企业曝光、增值服务

## 6. 重点竞品：求职方舟 AI

### 6.1 公开定位

求职方舟 AI 的公开定位是 AI 求职工具集合站，主要服务应届生和大学生求职。

它不是单一简历工具，而是把 AI 填简历、AI 找工作、AI 改简历、校招实习信息表、内推码表、投递进展表、会员体系组合在一起。

### 6.2 功能拆解

| 模块 | 求职方舟公开功能 | 解决的用户问题 | 对 Offer 罗盘的启发 |
|---|---|---|---|
| AI 填简历 | 浏览器插件，一键填写企业招聘官网表单 | 网申重复填表成本高 | 痛点真实，但插件成本高，暂不优先 |
| AI 找工作 | 上传简历或输入需求，AI 检索岗位 | 用户不知道去哪找合适岗位 | 我们先做精选岗位库和推荐，不急着全网检索 |
| AI 改简历 | 通用优化、专岗优化、过机筛优化 | 简历不会针对 JD 改 | 我们要做深 JD 匹配、投递准备度、版本迭代 |
| 校招汇总表 | 在线 Excel 式校招信息表 | 岗位信息分散 | 我们必须补强岗位数据和筛选 |
| 实习汇总表 | 实习岗位信息持续更新 | 找实习信息成本高 | 可做成招聘日历的子模块 |
| 内推码汇总表 | 收集企业内推码 | 学生缺少投递入口 | 可作为岗位详情增强信息 |
| 投递进展表 | 管理所有投递状态 | 海投后忘记进度 | 我们已经开始做，必须升级为核心闭环 |
| 笔试面试工具 | 与第三方合作，提供 AI 笔面试助力 | 笔试面试准备焦虑 | 我们应做合规的模拟面试和复盘，不做作弊式工具 |
| 会员体系 | AI 填简历会员、AI 找工作会员、全站会员 | 将高频功能变现 | 后期参考权益结构，不急着接支付 |
| 兑换码/支付 | 兑换码、订单、会员状态 | 校园推广和付费闭环 | 后期可用于试点和老师发码 |

### 6.3 它做得好的地方

1. 功能覆盖完整，已经不是 Demo，而是工具集合。
2. 直接抓住大学生高频痛点：简历、网申、岗位、投递、内推、笔试面试。
3. 商业闭环清晰，有会员、兑换码、支付、功能分层。
4. 信息表能力很实用，校招、实习、内推码天然适合学生传播。
5. 投递进展表能提高用户留存，不是一次性工具。

### 6.4 它可能存在的问题

1. 工具集合容易分散，用户可能不知道从哪里开始。
2. AI 填简历插件虽然强，但安装和兼容门槛高。
3. 自动找工作如果数据质量不稳定，用户信任会下降。
4. 如果过度强调“AI 替你做”，可能削弱用户自己的求职能力成长。
5. 笔试面试助力工具可能存在合规争议，尤其是在线笔试场景。

### 6.5 我们不能照抄的地方

1. 不能复制它的页面文案、视觉、资源和代码。
2. 不能一开始就做浏览器插件。
3. 不能过早做支付会员系统。
4. 不能做可能涉及作弊边界的笔试工具。
5. 不能把自己做成“低配求职方舟”。

## 9. 暂时不做的高成本能力

| 功能 | 暂时不做的原因 | 后续触发条件 |
|---|---|---|
| 自动填简历插件 | 浏览器插件兼容成本高，容易拖慢主线 | 核心闭环稳定且用户明确高频网申 |
| 自动投递 | 涉及账号、平台规则和合规风险 | 先做投递提醒和半自动管理 |
| 支付系统 | 现在还没验证付费意愿 | 有真实用户和明确权益后 |
| 全网岗位爬取 | 数据清洗、反爬、真实性维护复杂 | 先做精选岗位表和人工维护样本 |
| 笔试实时助力 | 可能触碰合规争议 | 只做备考资料和模拟训练 |
| 企业端后台 | 当前没有企业客户 | 有岗位流量和企业需求后再做 |

## 10. 产品差异化策略

### 10.1 定位差异

求职方舟更像 AI 求职工具集合站。

Offer 罗盘应该定位为：大学生求职作战系统。

差异不在功能名字，而在工作流：

岗位选择 → JD 拆解 → 简历匹配 → 投递准备度 → 简历版本 → 投递跟进 → 模拟面试 → 复盘画像 → 下一轮推荐。

### 10.2 体验差异

我们应该避免用户进入产品后不知道先点哪里。

核心体验应该是：

1. 用户先选择一个具体岗位或粘贴 JD。
2. 系统告诉他这份岗位到底要什么。
3. 系统判断他的简历能不能投。
4. 用户修改后加入投递表。
5. 面试前系统根据该岗位训练他。
6. 面试后沉淀复盘。

### 10.3 数据差异

不要只存“用户用过功能”，要存“用户求职过程”。

关键数据：

- 目标岗位
- JD 关键词
- 简历匹配分
- 投递准备度
- 投递状态
- 面试评分
- 失败原因
- 下一步建议

这些数据能形成用户画像，也是未来商业化和学校合作的基础。

## 11. 会员商业化路径

### 阶段 1：免费验证

目标：先验证产品是否真的解决问题。

免费提供：

- 基础简历分析
- 基础模拟面试
- 基础岗位列表
- 基础投递进展表

观察指标：

- 用户是否完整走完一次求职流程
- 是否重复分析不同 JD
- 是否主动记录投递进展
- 是否查看面试复盘

### 阶段 2：轻会员

目标：验证付费意愿。

可收费权益：

- 更多简历分析次数
- 专岗深度优化
- 简历版本管理
- 面试复盘报告导出
- 投递截止提醒
- 岗位推荐优先

### 阶段 3：全站会员

目标：形成稳定收入。

权益组合：

- 简历优化会员
- 面试训练会员
- 求职作战会员
- 全站会员

### 阶段 4：校园与企业合作

目标：从 C 端工具升级为就业服务工具。

合作方向：

- 创新创业学院试点
- 就业指导中心试点
- 二级学院求职训练营
- 企业岗位曝光
- 培训机构合作
- 校园社群推广

## 12. 校园创新创业推广路径

### 12.1 给指导老师看的表达

Offer 罗盘不是一个普通 AI 简历工具，而是一个面向大学生的求职作战系统。它把学生从看到岗位到准备简历、投递、面试、复盘的完整过程数字化，帮助学生用更有方法的方式求职。

### 12.2 老师最关心的问题

| 老师关心点 | 我们的回答 |
|---|---|
| 有没有真实需求 | 大学生求职普遍存在简历不会改、岗位不会选、面试不会复盘的问题 |
| 有没有竞品验证 | 求职方舟等产品已经验证 AI 求职工具集合站和会员闭环可行 |
| 有没有差异化 | 我们不做单点工具，做求职工作流闭环和复盘画像 |
| 能不能落地 | 当前已有 Demo，下一步可在学院内做小范围试点 |
| 有没有商业价值 | 可做学生会员、校园合作、企业曝光、增值服务 |

### 12.3 校园试点方案

第一批试点用户：

- 正在找实习的大二、大三学生
- 准备秋招的大三、大四学生
- 简历薄弱但有项目经历的学生
- 面试表达弱的学生

试点流程：

1. 收集用户简历和目标岗位。
2. 让用户完成一次 JD 匹配分析。
3. 让用户根据建议改一版简历。
4. 将岗位加入投递进展表。
5. 做一次模拟面试。
6. 生成复盘结果。
7. 记录用户反馈。

试点产出：

- 用户使用前后对比
- 简历修改前后对比
- 面试回答前后对比
- 投递进展数据
- 用户访谈材料
- 老师汇报材料

## 14. 阶段性结论

老师的建议是正确的：现在不能只凭兴奋继续往前冲，要先把市场上的产品看完、拆透，再决定功能优先级。

Offer 罗盘继续做有价值，但必须坚持三点：

1. 不做低配版竞品。
2. 不做功能堆叠。
3. 做大学生求职工作流闭环。

下一阶段的核心不是“多加几个功能”，而是让真实学生完整走完一次流程：

岗位选择 → JD 分析 → 简历优化 → 加入投递 → 模拟面试 → 结果复盘 → 下一轮优化。

只要这个闭环跑通，项目就有继续投入、参加创新创业项目和争取老师资源的价值。
