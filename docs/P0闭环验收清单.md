# Offer 罗盘 P0 闭环验收清单

## 0. 验收目标

本清单只验收 Offer 罗盘当前最核心的一条 P0 主工作流：

> 外部岗位/JD -> 简历匹配分析 -> 投递准备度判断 -> 改写建议 -> 保存简历版本 -> 加入投递进展 -> JD 模拟面试 -> 面试复盘 -> 求职诊断档案 -> 反哺下一版简历和下一次投递。

P0 的判断标准不是“页面看起来有功能”，而是用户能不能完成一次真实求职闭环：

1. 用户拿到一个具体岗位或 JD。
2. 用户用自己的简历和该 JD 做匹配分析。
3. 系统判断这份简历是否已经适合投递。
4. 系统给出可执行的改写建议。
5. 用户保存这一版“针对某个岗位的简历版本”。
6. 用户把岗位加入投递进展。
7. 用户基于同一份 JD 和简历版本进行模拟面试。
8. 系统生成面试复盘。
9. 系统沉淀求职诊断档案。
10. 求职诊断档案反过来指导下一版简历和下一次投递。

## 1. 完成状态定义

| 状态 | 判断标准 |
|---|---|
| 已完成 | 用户可以在页面上独立完成该步骤；刷新后关键结果不丢失；该步骤能和前后步骤形成明确链路。 |
| 部分完成 | 页面或数据结构已经存在，但链路不完整、持久化不足、上下文绑定不强，或者只能完成演示级流程。 |
| 未完成 | 用户无法在当前产品中完成该步骤，或只能靠人工记录、临时复制粘贴、开发者解释来完成。 |

## 3. 单步详细验收

### 3.1 外部岗位 / JD

- 用户验收标准：
  - 用户可以粘贴一个具体 JD。
  - 用户可以从岗位列表选择一个具体岗位。
  - 岗位信息至少包含岗位名称、公司、JD/要求、截止时间或来源信息。
- 页面 / 文件 / 数据位置：
  - 页面：简历分析页、岗位日历页。
  - 文件：`frontend/src/views/Resume.vue`、`frontend/src/views/Calendar.vue`、`frontend/src/stores/jobs.js`、`backend/main.py`。
  - 数据：岗位列表、浏览记录、JD 输入框内容。
- 已完成判定：用户能从真实岗位或完整 JD 进入后续分析。
- 部分完成判定：只能粘贴 JD 或使用内置岗位，不能稳定解析外部链接。
- 未完成判定：用户只能选择抽象方向，无法绑定具体岗位。
- 当前状态：部分完成。
- 下一步开发动作：先强化“粘贴 JD / 选择岗位”链路；外部链接解析先作为 P1，不要打断 P0。

### 3.2 简历匹配分析

- 用户验收标准：
  - 用户上传或粘贴简历后，系统能结合具体 JD 给出匹配度。
  - 分析结果要包含匹配分数、优势、缺口、风险项。
  - 结果必须能解释“为什么适合 / 不适合这个岗位”。
- 页面 / 文件 / 数据位置：
  - 页面：简历分析页。
  - 文件：`frontend/src/views/Resume.vue`、`frontend/src/stores/resume.js`、`frontend/src/api/resume.js`、`backend/main.py`。
  - 数据：`resume_history`、当前分析结果状态。
- 已完成判定：同一份简历面对不同 JD，输出会明显不同。
- 部分完成判定：能输出分析，但内容仍偏通用。
- 未完成判定：只能做简历润色，不能结合 JD。
- 当前状态：部分完成。
- 下一步开发动作：验收 Prompt 和后端返回结构，确保每条建议绑定 JD 要求。

### 3.3 投递准备度判断

- 用户验收标准：
  - 用户能看到“建议投递 / 暂缓投递 / 不建议投递”等明确判断。
  - 判断后必须说明原因，不允许只有分数。
  - 如果用户盲目自信，系统必须指出关键风险。
- 页面 / 文件 / 数据位置：
  - 页面：简历分析结果区。
  - 文件：`frontend/src/views/Resume.vue`、`backend/main.py`。
  - 数据：`readiness`、`readiness_label`、`readiness_level`、`readiness_reason`。
- 已完成判定：用户不用懂简历，也能知道投递风险。
- 部分完成判定：有准备度字段，但判断不够具体。
- 未完成判定：只有匹配分，没有投递决策建议。
- 当前状态：部分完成。
- 下一步开发动作：把准备度作为“改写建议前的判断标语”，再承接具体建议。

### 3.4 改写建议

- 用户验收标准：
  - 用户能看到针对 JD 的分条改写建议。
  - 建议必须能落到简历模块，例如项目经历、技能关键词、量化成果、岗位关键词。
  - 不直接替用户输出最终简历全文，避免用户失去判断能力。
- 页面 / 文件 / 数据位置：
  - 页面：简历分析结果区。
  - 文件：`frontend/src/views/Resume.vue`、`frontend/src/stores/resume.js`、`backend/main.py`。
  - 数据：`rewrite_templates`、`suggestions`。
- 已完成判定：用户能按建议回去修改自己的简历。
- 部分完成判定：建议存在但模板化、泛泛而谈。
- 未完成判定：只有一句“建议优化简历”。
- 当前状态：部分完成。
- 下一步开发动作：统一命名为“改写建议”，并检查建议是否具体到简历字段。

### 3.5 保存简历版本

- 用户验收标准：
  - 用户可以保存“针对某个 JD 的简历版本”。
  - 版本里要记录岗位、JD 摘要、匹配分、准备度、改写建议和创建时间。
  - 用户后续能从个人页或历史记录找回。
- 页面 / 文件 / 数据位置：
  - 页面：简历分析页、个人页。
  - 文件：`frontend/src/stores/resume.js`、`frontend/src/views/Resume.vue`、`frontend/src/views/Profile.vue`。
  - 数据：`offer_compass_resume_versions`、`resume_history`。
- 已完成判定：版本能保存、查看、用于后续投递和面试。
- 部分完成判定：版本能本地保存，但未和投递记录、面试记录强绑定。
- 未完成判定：用户每次分析后结果都会丢失。
- 当前状态：部分完成。
- 下一步开发动作：给投递记录增加 `resumeVersionId`，让每次投递对应一版简历。

### 3.6 加入投递进展

- 用户验收标准：
  - 用户可以把岗位加入投递进展表。
  - 用户可以修改阶段：已加入、已投递、笔试、面试、Offer、未通过。
  - 刷新页面后投递记录不丢失。
- 页面 / 文件 / 数据位置：
  - 页面：岗位日历页 / 投递进展表。
  - 文件：`frontend/src/views/Calendar.vue`、`frontend/src/stores/jobs.js`、`frontend/src/api/jobs.js`、`backend/main.py`。
  - 数据：`offer_compass_application_records`。
- 已完成判定：记录可增删改查，并能持续存在。
- 部分完成判定：本地可用，但没有后端持久化和账号级同步。
- 未完成判定：只能看岗位，不能管理投递。
- 当前状态：部分完成。
- 下一步开发动作：先补“投递记录绑定 JD + 简历版本 + 面试记录”的数据字段，再考虑后端表。

### 3.7 JD 模拟面试

- 用户验收标准：
  - 用户能从某个岗位或简历版本进入模拟面试。
  - 面试问题要围绕 JD、简历经历和岗位要求。
  - 面试开始页要显示当前绑定的岗位上下文，避免用户不知道在面哪个岗位。
- 页面 / 文件 / 数据位置：
  - 页面：模拟面试页。
  - 文件：`frontend/src/views/Interview.vue`、`frontend/src/stores/interview.js`、`frontend/src/api/interview.js`、`backend/main.py`。
  - 数据：`offer_compass_interview_context`、`resume_interview_context`、`interview_history`。
- 已完成判定：面试问题明显引用当前 JD 和简历。
- 部分完成判定：能带上下文启动，但刷新或跨页面后上下文容易断。
- 未完成判定：只能做通用岗位面试。
- 当前状态：部分完成。
- 下一步开发动作：让面试记录保存 `jobId`、`resumeVersionId`、`applicationRecordId`。

### 3.8 面试复盘

- 用户验收标准：
  - 面试完成后生成结构化复盘。
  - 复盘至少包含命中点、最大问题、薄弱项、简历改写线索、下一步行动。
  - 用户能在历史记录中重新查看。
- 页面 / 文件 / 数据位置：
  - 页面：模拟面试页、个人页。
  - 文件：`frontend/src/views/Interview.vue`、`frontend/src/stores/interview.js`、`frontend/src/views/Profile.vue`、`backend/main.py`。
  - 数据：`interview_history`、`offer_compass_interview_reviews`。
- 已完成判定：复盘能指导用户下一次回答和简历修改。
- 部分完成判定：复盘存在，但没有和下一轮简历分析形成入口。
- 未完成判定：只有单轮反馈，没有总结。
- 当前状态：部分完成。
- 下一步开发动作：在复盘结果中增加“去优化这版简历 / 加入下一步计划”的入口。

### 3.9 求职诊断档案

- 用户验收标准：
  - 用户能看到自己长期求职中的优势、短板、常见失败原因和适配岗位倾向。
  - 诊断档案来自简历分析、投递进展、模拟面试和复盘，而不是用户手填标签。
  - 诊断档案能更新，不是一张静态信息卡。
- 页面 / 文件 / 数据位置：
  - 页面：个人页。
  - 文件：`frontend/src/views/Profile.vue`、`frontend/src/stores/resume.js`、`frontend/src/stores/interview.js`、`frontend/src/stores/jobs.js`、`backend/main.py`。
  - 数据：`offer_compass_user_profile_signals`、历史记录、统计接口。
- 已完成判定：诊断档案能解释“你下一步该怎么改”。
- 部分完成判定：有历史记录和统计，但没有形成诊断档案结论。
- 未完成判定：个人页只是账号信息页。
- 当前状态：部分完成。
- 下一步开发动作：把复盘中的 `weakness_tags`、`resume_rewrite_clues`、`next_actions` 聚合成诊断档案面板。

### 3.10 反哺下一版简历和下一次投递

- 用户验收标准：
  - 用户能从诊断档案或复盘直接进入下一次简历优化。
  - 系统能提醒用户下一次投递应规避什么问题。
  - 下一版简历分析能继承上一轮复盘线索。
- 页面 / 文件 / 数据位置：
  - 页面：个人页、简历分析页、岗位日历页。
  - 文件：`frontend/src/views/Profile.vue`、`frontend/src/views/Resume.vue`、`frontend/src/views/Calendar.vue`、`frontend/src/stores/interview.js`、`frontend/src/stores/resume.js`。
  - 数据：简历版本、面试复盘、投递记录、诊断档案信号。
- 已完成判定：用户完成一次面试复盘后，能自然进入下一轮简历优化和投递。
- 部分完成判定：数据存在，但需要用户自己复制粘贴和理解。
- 未完成判定：流程在复盘后结束，没有下一步。
- 当前状态：未完成。
- 下一步开发动作：增加“根据复盘优化简历”和“推荐下一步投递动作”的入口。

## 4. 当前最该补的 3 个缺口

### 缺口 1：投递进展表缺少强绑定数据结构

- 问题：投递记录目前可以本地保存阶段，但没有稳定绑定 `JD / 简历版本 / 面试记录 / 复盘记录`。
- 影响：用户看似有投递表，但无法回答“我投这个岗位时用的是哪一版简历、面试暴露了什么问题”。
- 下一步：给投递记录补字段：`jobId`、`resumeVersionId`、`interviewId`、`reviewId`、`source`、`deadline`、`nextAction`。

### 缺口 2：JD 模拟面试上下文还不够硬

- 问题：当前上下文主要依赖 `sessionStorage` / `localStorage`，可以演示，但不是稳定业务链路。
- 影响：一旦刷新、换入口、跨设备，用户可能不知道自己正在基于哪份 JD 和哪版简历面试。
- 下一步：面试启动必须带上 `jobId` 和 `resumeVersionId`，面试历史也要保存这两个字段。

### 缺口 3：求职诊断档案没有形成明确反哺动作

- 问题：复盘和诊断档案信号已经有雏形，但用户看不到一个清晰结论：我下一版简历该改什么，下一次投递该避开什么。
- 影响：产品闭环停在“记录”和“分析”，没有进入“持续变强”。
- 下一步：个人页新增诊断档案面板，聚合薄弱项、简历改写线索、岗位适配方向，并提供跳转到简历优化的入口。

## 5. P0 回归验收脚本

每次 P0 改动后，按以下顺序人工验收：

1. 打开简历分析页。
2. 粘贴一个具体 JD，上传或粘贴一份简历。
3. 点击分析，确认出现匹配分、优势、缺口、投递准备度、改写建议。
4. 判断投递准备度是否足够具体，是否能阻止明显不适合的盲目投递。
5. 保存当前分析为岗位专属简历版本。
6. 打开岗位日历页，把同一岗位加入投递进展表。
7. 修改投递阶段，刷新页面，确认记录仍存在。
8. 从岗位或简历版本进入模拟面试。
9. 确认模拟面试页展示当前 JD / 岗位上下文。
10. 完成一次模拟面试，查看结构化复盘。
11. 打开个人页，确认能看到简历历史、面试历史、投递记录或诊断档案信号。
12. 检查用户是否能从复盘或诊断档案自然进入下一轮简历优化。

## 6. P0 暂不做清单

以下功能不是当前 P0，不应抢占主流程开发资源：

1. 自动投递。
2. 自动填写第三方招聘网站表单。
3. 大规模招聘网站爬虫。
4. 会员支付和订阅体系。
5. 简历模板商城。
6. 复杂 BI 数据大屏。
7. 多端同步和企业级权限系统。

这些功能可以成为 P1 / P2，但当前阶段必须先把“JD -> 简历 -> 投递 -> 面试 -> 复盘 -> 诊断档案 -> 下一轮优化”的闭环打穿。

## 7. 验收结论

当前项目不是“没有功能”，而是多个功能点已经存在，但链路仍偏松：简历分析、岗位进展、模拟面试、个人页诊断档案之间还没有完全形成同一条数据链。

P0 下一阶段的正确开发方向是：

1. 不急着加新功能。
2. 先补绑定关系。
3. 先让一次真实求职过程可以完整走通。
4. 再扩展岗位数据、商业化、自动化和部署能力。
